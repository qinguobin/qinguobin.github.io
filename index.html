踩坑全记录：34 个坑

发表于 2026-10-17

从"想做个企微消息提醒"到交付，踩了 30 多个坑。按类别整理，每类都写了 症状 → 根因 → 解法，你可以直接跳到需要的部分。

一、环境与依赖

1. WorkBuddy 自带的 Python 3.13 没有 tkinter

症状：小组件（唯一可选的 GUI 方案）一跑就 ModuleNotFoundError: No module named 'tkinter'。 根因：官方 Python 3.13 的 Windows 构建里，tkinter 是可选组件，这个版本没带。 解法：静默安装官方 Python 3.12 到 D 盘（顺带满足"软件不占 C 盘"的要求）：

Include_tcltk=1 就是关键——默认静默安装不带 tk。

2. venv 反复创建失败

症状：python -m venv 在 D 盘上死活创建不出来，换 --clear 也不行。 根因：环境限制，venv 的创建路径/权限在本机不通。 解法：放弃 venv，直接把依赖装进 D:\Python312 本体。 代价：遗留了一个 60MB 的废弃目录（已重命名为 _unused_venv_can_delete 提示可删）。

3. Pillow 装不上

症状：pip install pillow 失败。 解法：不装了。用标准库 zlib + struct 手写 PNG 编码，30 行搞定，零依赖。

4. pyesedb 编译装不上

症状：想直接读 Windows 通知历史库 wpndatabase.db（ESE 格式），pip install pyesedb 失败。 影响：通知历史这条路直接放弃（后来证明这条路本来也是死路）。

5. wecom-cli 不在 Windows 的 PATH 里

症状：Python 的 subprocess.run(["wecom-cli", ...]) 找不到命令， 但在 Git Bash 里直接敲却能用。 根因：它只加到了 Git Bash 的环境，没进系统 PATH。 解法：调用时写完整路径 + .cmd 后缀：

二、64 位下的 ctypes 经典陷阱

6. 剪贴板永远读到空字符串 ★ 最隐蔽的一个

症状：写入剪贴板后立刻读回，永远是 ""，但系统剪贴板里内容是对的。 根因：64 位下 ctypes 函数默认 restype 是 c_int（32 位）， GetClipboardData 和 GlobalLock 返回的 64 位句柄被截断成低 32 位， 拿到的是个野指针。

解法：必须显式声明返回类型。

这个 bug 害得我一度误判"Ctrl+F 唤起企微搜索框失败"——其实是回读验证的 代码本身有问题，快捷键一直是好的。

通用教训：在 64 位 Windows 上，任何返回指针/句柄的 Win32 函数， 用 ctypes 调都必须显式设 restype，否则句柄会被截断。

7. BITMAPINFOHEADER 打包格式错

症状：GetDIBits 出来的图是花的或全黑。 根因：struct.pack 格式串必须是小端 <IiiHHIIiiII，写成 "IiiHHIIiiII" （本机字节序）在某些场景下会错位。 解法：显式加 < 前缀。

三、读取企业微信消息

8. 企微是 Flutter 渲染，UIA 只能读到 2 个空节点 ★ 根本性障碍

影响：

  • 读不到任何聊天文本 → 无法自动监听消息；
  • 点不动任何会话 → "右键标记为已读"这条路废掉，改走快捷键。

绕过：Flutter 最终要把像素画到窗口上 → 走屏幕截图 + OCR。

9. 会话存档接口 853006：企业没开通，不是你没授权

症状：

关键推理（省了我半天时间）：我用 4 个 chat-id 试，其中 3 个是瞎编的 （wmXXXX / test），全部返回同一个错误码。这说明拦截发生在 校验 chat-id 之前——是企业层级的功能开关，不是参数问题、也不是授权问题。

结论：连接器只能发消息，读不了你和同事的聊天记录。 想让它能读，需要企业管理员去开「会话内容存档」（付费功能）。

10. 全量普查证明：连接器里根本没有"收消息"命令

唯一能用的读类接口 message aibot sessions list 只返回机器人自己会话的 元数据（chat_id / chat_name / chat_type / last_msg_time）， 没有任何命令能读这些会话的消息正文。

11. 通讯录接口 850002

contact users search → 850002，机器人未被授权「通讯录」。 （但如 §9 所述，就算授了权，853006 依然在，聊天记录还是读不了。）

12. 企微在本机根本不弹系统通知

症状：通知探针跑 150s / 180s / 240s，一条企微通知都没抓到。 影响："捕获系统 Toast 通知"这条路断了——原本以为它是唯一能绕开 Flutter 限制的通道（通知是系统渲染的）。

13. 抓到的是过期画面 —— "发了消息没反应"的真凶 ★

症状：用户发消息，程序毫无反应；手动截图看画面是对的。 根因：用 BitBlt 抓窗口，对 Flutter（走 DirectComposition 合成） 只能拿到过期的那一帧。

解法：用 PrintWindow 的 PW_RENDERFULLCONTENT 标志强制重渲染。

14. 最小化 / 移到屏幕外 = 画面冻结 ★ 推翻了我的错误判断

我最初以为"用 PrintWindow 连最小化也能读到"，实测是错的。 用内容指纹做的受控实验（用户发消息，我盯着指纹变不变）：

企微窗口状态 结果
显示在屏幕 + 消息页 ✅ 指纹随新消息变化
最小化到任务栏 ❌ 70 秒纹丝不动
移到屏幕外（未最小化） ❌ 2.5 分钟不动，移回屏幕立刻变化
切到「工作台/文档」页 ❌ 没有会话列表
被其它窗口盖住 ✅ 仍可读
在另一个虚拟桌面 ✅ 仍可读

好消息：被盖住 / 在别的虚拟桌面都不影响，所以可以把它藏在后面眼不见为净。

15. 最小化时 GetWindowRect 返回的坐标不靠谱

症状：截图尺寸塌成 314x50（微信）或 -32000（企微）。 根因：最小化时 GetWindowRect 返回的是任务栏图标的小矩形， 或 (-32000, -32000) 这种"不存在"坐标。

解法：用 GetWindowPlacement 拿 rcNormalPosition（还原后的矩形）：

IsIconic(hwnd) 这个判断是后来测微信时才补上的。

16. 误把「工作台」页面当成消息列表，生成了一堆垃圾待办

症状：小组件显示"待处理 2 条"，但点开什么都没有。 根因：企微有多个标题都叫「企业微信」的窗口，程序没判断当前停在哪个页， 把工作台页的"审批""智能机器人""打卡"当成了消息。 解法：加 is_chat_view() 判断——靠会话列表右侧的时间戳特征 （刚刚 / xx分钟前 / 昨天 / xx:xx）来确认当前是消息页， 切到工作台/文档页自动跳过并清空基线。

第一版判断是找顶部的"未读/@我/单聊/群聊"筛选条，太严了， 实测布局里筛选条位置对不上，导致本该能读的也跳过了。改用时间戳特征才稳。

17. OCR 对 12px 小字识别率很差

截图原图很清晰，但 OCR 出来一堆错字。 解法：GDI HALFTONE 模式高质量放大 2 倍再送 OCR，识别质量可用 （人名偶有误差，消息正文基本准确）。放大 3 倍提升有限但更慢。

18. WinRT 的 IAsyncOperation 不能自己造 event loop

症状：用 asyncio.new_event_loop().run_until_complete(await ...) 卡死。 解法：改用事件驱动同步等待（设事件 → 触发 → 等待 → 取结果）。

19. OCR 出来的名字是错字，@我 判断漏判

症状：@秦国彬 被 OCR 成 @泰国彬 / @孬王彬 / @癸国彬，精确匹配全部漏掉。 解法：difflib 模糊匹配，相似度阈值内都算命中。 （代价：群名也可能被误匹配，所以同时保留了 group_senders 白名单。）

20. 截图有透明通道时 OCR 拿到全透明图

症状：OCR 返回 0 行。 根因：窗口截图 alpha 通道是 0，OCR 引擎认为整图透明。 解法：强制把 alpha 填成不透明：

四、桌面小组件（tkinter）

21. 收起时把 34px 高度存进了 geometry

症状：收起小组件后重启，窗口只剩一条标题栏，内容全没了。 根因：收起状态也保存了窗口尺寸（34px = 只有标题条的高度）。 解法：收起状态不保存尺寸，且载入几何时强制最小高度 200px。

22. 收起后只能双击展开，用户以为点不动

症状：用户说"点击也没有反应"。 解法：收起时改成单击标题条即展开。（原来绑的是双击，且没有任何提示。）

23. 卡片合并后，勾掉单条时删除线画错了

症状：勾掉后连复选框本身也被划掉。 解法：遍历行内 Label 时跳过 ☑ 本身。

24. 卡片合并的 pack 顺序

收起/展开时 list_frame 和 footer 的 pack 顺序会乱，要用 before= 指定顺序。

五、消息判定

25. 关键词把「无需回复」误判成需要处理

症状："公司年会照片已上传，无需回复" → 判定为待办。 根因：命中了"回复"两个字。 解法：加否定词排除——先扫否定词（无需 / 不用 / 不必 / 已通过 …）， 命中就直接判为无需处理。

26. 「@所有人」被当成「@我」

症状：群里的 @所有人 明天团建 也被钉到桌面。 解法：只认 @你本人（昵称来自 config.json 的 filter.my_names）， @所有人 / @全体成员 一律不算。AI 提示词里也写死了这条规则。

27. 勾掉后消角标：Flutter 下 UIA 无效

企微没有开放"标记已读"的接口。两级策略：

  1. UIA 找会话 → 右键 → "标记为已读"（Flutter 下基本用不上）
  2. 快捷键（主路线）：激活企微 → Ctrl+F 唤起搜索 → 粘贴会话名 → 回车打开会话 → 角标清除 → Esc → 切回原窗口

Ctrl+F 这条实测通过（用"选中 → 复制回读"的方式验证，避免截图验证）。 不灵时可换 Ctrl+K，或直接设 click_search_offset 用鼠标点搜索框。

六、进程与自启动

28. 自动化环境拉起的进程全部存活不下来 ★ 影响交付方式

症状：程序明明启动了、日志也写了，过一会儿就没了。 实测：

方式 结果
Start-Process 被安全策略拦截
wscript.exe 跑 VBS 被拦截
schtasks /create /sc onlogon 直接被拉黑

解法：必须由用户双击 Start.bat 启动，或等下次开机（Startup 的 VBS 已装好）。 这条直接改变了交付方式——我不能替用户把程序跑起来。

29. 多个实例同时跑导致重复捕获

症状：日志里每条消息重复出现、CPU 飙高。 根因：反复重启时旧进程没杀干净。 解法：用 WMI Win32_Process 按命令行特征批量清理，且每次重启前删 app.pid。

30. 改了代码但进程里跑的是旧版本

症状：traceback 的行号跟源码对不上，改了就是不生效。 解法：重启前先删 __pycache__。

七、个人微信

31. 个人微信官方就没有开放读取聊天记录的 API ★ 根本障碍

微信只开放了三类 API：公众号、小程序、企业微信，个人账号的聊天记录不在其中。 所以不存在"授权某个应用读我的微信消息"这个动作—— 用户问"需要授权吗"，答案是"不需要，也无处可授权"。

32. 微信 4.0 是 Qt + 自绘，UIA 同样空

33. 微信本地数据库全部 SQLCipher 加密

Documents\WeChat Files\<wxid>\Msg\ 下 12 个库（含 ChatMsg.db）， 文件头全部不是 SQLite format 3。

34. 微信最小化时截图是纯色空图

最值钱的三个教训

  1. 先证明"能不能"，再动手做。 我在"企微最小化也能读到"这个错误判断上 浪费了最多时间——先做 30 秒的受控实验（内容指纹），能省掉后面几小时。

  2. 64 位 + ctypes 必须显式声明 restype。 句柄截断的表现极具迷惑性 （读出来是空字符串，看起来像"功能不支持"）。

  3. 报错码要会读。 853006 用 4 个不同 ID 测试结果相同 → 立刻能断定是 企业层开关，而不是"我的参数写错了"，省掉了无意义的调试。

全过程记录：把企微消息钉到桌面

发表于 2026-10-17

一个"把企业微信消息钉到桌面"的需求，从提出到交付的完整过程。 时间跨度约 1.5 小时，中间推翻了自己两次判断。

需求的 15 次演进

# 需求 我的处理
1 企微收到消息 → 识别是否需要处理 → 固定在桌面 立项。UI 自动化 + AI 判断 + tkinter 小组件
2 软件和数据存 D 盘，不占 C 盘 项目迁到 D:\WeComDesktopAlert，Python 装到 D:\Python312
3 群消息只收 @我 的 加 mentions_me()；后来发现 @所有人 也算，修正
4 小组件要有一键勾掉 卡片头 ☐ 勾掉整个会话 + 行首 ☐ 勾掉单条
5 打开企业微信时自动运行 加 watchdog.py 监听 WXWork.exe 进程
6 同一人的多条消息合并到一张卡，按时间排序 重写 widget.py，从"一条一框"改成"一会话一卡"
7 勾掉时清企微角标；但企微里先已读不能移除桌面内容 加 markread.py（快捷键路线）；明确不做"因企微已读而删除"
8 "我已经用了企微连接器，你为何不用它读消息？" 全量实测连接器 → 853006，证明读不了
9 不在消息界面 / 最小化时怎么读 改用 PrintWindow；随后实测发现最小化仍冻结，推翻自己的结论
10 是不是必须开着企微且在消息页才能读到 做受控实验，给出硬边界表格
11 "这完全偏离了我的初衷，我要任何时候只要登录就必须查到" 承认做不到，指出唯一出路是「会话内容存档」，预留 apiread.py
12 连接器能读到企微消息吗 用 4 个 chat-id 证明是企业层开关（853006）
13 微信消息你能读到吗 实测：Qt + 自绘 + SQLCipher，读不到
14 需要我的微信做什么授权吗 不需要 —— 个人微信官方没有这个 API，授权无处可授
15 把全过程和踩坑发到 GitHub 本文档

两次自我推翻： - 第一次：以为 PrintWindow 能突破最小化 → 实测证明最小化依然冻结。 - 第二次：以为企微必然停在"工作台"页 → 实际它在消息页， 是我第一版 is_chat_view() 的判断条件写得太严，导致本该能读的也跳过了。

三个阶段

阶段一：按直觉做（02:05 – 02:30）

照着常规思路搭：UIA 读企微控件 → AI 判断 → tkinter 小组件。 tkinter 装不上是第一个拦路虎，装了官方 Python 3.12 才通。

产物：main.py / widget.py / classifier.py / storage.py / watcher.py。

这个阶段做完了，但它是错的——UIA 根本读不到企微内容。

阶段二：撞墙与换路（02:30 – 03:15）

发现企微是 Flutter，UIA 只能读到 2 个空节点。于是依次尝试：

  1. 企微连接器 → 853006（企业未开通会话存档）
  2. Windows 通知 → 探针跑 240 秒，一条没抓到
  3. 屏幕截图 + OCR → 走通了

同时补上用户陆续提的需求（卡片合并、勾掉、消角标、自动启停）。

阶段三：实证与收敛（03:15 – 03:35）

用户连续追问核心问题（"不在消息页怎么读"、"是不是必须开着"、 "连接器能读吗"、"微信呢"）。每问一次就做一次实测，最终把能力边界 画成了一张明确的表格，并把结论写进 README 和 PITFALLS。

最终架构

辅助模块：

  • watchdog.py：监听 WXWork.exe，企微开 → 拉起程序；企微关 → 退出

  • apiread.py：预留的会话存档读取模块，企业一开通就能用， 遇到 853006 自动静默停用

  • selftest.py：界面自检（卡片合并 / 勾掉 / 收起）

最终结论

能做到的（窗口可见时全自动）：

  • 自动捕获新消息 → AI 判断 → 钉到桌面 → 一键勾掉 → 顺带清企微角标

做不到的（客观限制，不是代码问题）：

  • 企微最小化 / 移出屏幕时读不到（Flutter 停止渲染）
  • 企微停在工作台页时读不到
  • 用官方接口读聊天记录（企业未开通会话存档 853006）
  • 读个人微信消息（官方无此 API，本地库 SQLCipher 加密）

唯一的根治方案：企业管理员开通「会话内容存档」（付费）， 开通后 apiread.py 直接可用，届时窗口状态完全无关。

企业微信消息识别 · 桌面置顶小组件

发表于 2026-10-17

把企业微信里需要你处理的消息钉在桌面最上层，处理完一键勾掉（顺带清掉企微里的未读角标）。

先看这三篇，能省你半天时间： - 📖 全过程记录 —— 需求怎么演进的，我推翻过自己哪两次判断 - 🔥 踩坑全记录 —— 34 个坑，每个都有「症状 → 根因 → 解法」 - 🔬 企微读取通道实测 —— 四条路，三条是死的

一句话结论：企微和微信的聊天记录，官方都不让你读。 本项目用「屏幕截图 + OCR」绕了过去，代价是——企微窗口必须真实显示在屏幕上。

一、它现在能做什么

功能 状态 说明

二、消息的四种进法（重要，请先读）

1. 屏幕捕获（主通道，全自动）

每 3 秒截图企微窗口 → 系统 OCR → 发现会话列表有新内容 → AI 判断 → 钉到桌面。 不需要你做任何操作。

但有硬边界（全部实测过）：

企微窗口状态 能不能读 说明
显示在屏幕 + 停在「消息」页 ✅ 哪怕被别的窗口盖住、或在另一个虚拟桌面，都不影响
被其它窗口完全盖住 ✅ PrintWindow 强制重渲染，不受遮挡影响
在另一个虚拟桌面 ✅ 同上
切到「工作台/文档」等页 ❌ 屏幕上没渲染消息列表，没像素就没内容
最小化到任务栏 ❌ 企微停止渲染，只能拿到冻结帧（实测 70 秒纹丝不动）
移到屏幕外（未最小化） ❌ 同样冻结（移回屏幕内立刻恢复）

所以用法是：企微开着、停在消息页、别最小化。 想让它"眼不见为净"，用别的窗口盖住它，或者扔到另一个虚拟桌面——这两种都照读不误。

当前状态会实时显示在标题栏上：企微已最小化（暂停） / 企微不在消息页。

2. 剪贴板（辅助，最精确）

在企微里右键消息 → 复制即可。

3. 全局热键（辅助，推荐）

在企微里选中那段消息文字 → 按 Ctrl+Alt+Space，程序替你在企微内执行复制。 只在焦点属于企微窗口时生效，不会把 Ctrl+C 打到别的程序里。

见 第六节。

发表于 2026-10-17

这是本项目唯一走通的自动读取方案。核心在 screen.py。

为什么它能绕开 Flutter / Qt

Flutter（企微）和 Qt 自绘（微信）都不向 UIA 暴露控件树， 但它们最终都要把像素画到窗口上。像素是绕不过去的。

所以流程是：

三个必须踩对的点

1. PrintWindow(PW_RENDERFULLCONTENT) 而不是 BitBlt

BitBlt 对 DirectComposition 合成的窗口只能拿到过期帧—— 这是"用户发了消息、程序毫无反应"的直接原因。

2. 最小化/屏外时要用还原矩形

最小化后 GetWindowRect 会返回垃圾坐标：

场景 GetWindowRect 返回值
企微最小化 (-32000, -32000)
微信最小化 314x50（小矩形，不是 -32000）

所以不能只判断 -32000，必须用 IsIconic：

3. 强制填充 alpha 通道

窗口截图的 alpha 是 0，OCR 引擎会当成全透明图，直接返回 0 行：

会话列表的定位

按 x 坐标区间 从整窗 OCR 结果里切出会话列表那一列（默认 x ∈ [0.15, 0.38]）， 再按 y 排序。构造 screen.py：

消息页判断 is_chat_view()

必须确认企微停在「消息」页，否则会把工作台页的"审批""打卡"当成消息。

第一版（错）：找顶部的"未读/@我/单聊/群聊"筛选条 → 太严， 实际布局里位置对不上，导致本该能读的也被跳过。

第二版（对）：找会话列表右侧的时间戳特征—— 刚刚 / N分钟前 / 昨天 / HH:MM / 昨天 HH:MM。

OCR 错字的模糊匹配

OCR 会把 @秦国彬 识别成 @泰国彬 / @孬王彬 / @癸国彬，精确匹配全漏。 用 difflib 做相似度匹配（阈值内算命中）。

副作用是群名也可能被误匹配，所以保留 filter.group_senders 白名单兜底。

目标：证明"能否在不操作鼠标键盘的前提下，自动读到企业微信里别人发来的消息"。

结论先行：只有「屏幕 OCR」一条路可用，且企微窗口必须真实显示在屏幕的「消息」页。

关键推理：4 个 ID 里有 3 个是瞎编的（wmXXXX / test），却返回同一个错误码， 说明拦截发生在校验 chat-id 之前，是企业层级的功能开关，不是参数问题：

全量普查（证明没有任何"收消息"命令存在）：

唯一能正常返回的读类接口是 message aibot sessions list，但它只返回机器人自己 会话的元数据，且当前为空，没有任何命令能读这些会话的消息正文：

顺带的坑：wecom-cli 只在 Git Bash 的 PATH 里，Windows 原生环境找不到， 从 Python subprocess 调用必须写完整路径 …\cli-connector-packages\wecom-cli.cmd。

企微的通知是系统层渲染的，理论上不受 Flutter 限制，能被 UIA 捕获。实测：

150～240 秒内企微一个通知窗口都没弹过。（前提是用户确实在此期间发了消息。）

之前还试过直接解析 Windows 通知历史库 %LOCALAPPDATA%\…\wpndatabase.db（ESE 格式）， 但 pyesedb 编译装不上，这条路也断了。

路径四：屏幕截图 + OCR —— ⚠️ 可用，但有硬边界

这是唯一走通的路。 原理：Flutter 虽然不暴露控件树，但它最终要把像素画到窗口上。

关键突破 1：用 PrintWindow 而非 BitBlt

一开始用 BitBlt 抓窗口，抓到的是过期帧（画面永远停在若干分钟前）， 这是"用户发了消息、程序毫无反应"的直接原因。

原因是 Flutter 走 DirectComposition 合成，普通 DC 拷贝拿不到当前内容。 改用 PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT) 强制重渲染后才拿到真实画面。

关键突破 2：OCR 前先放大 2 倍

Windows OCR 对 12px 小字识别率很差。用 GDI HALFTONE 模式高质量放大 2 倍后， 识别质量可用（人名偶有误差，消息正文基本准确）。

引擎用 Windows 自带的 Windows.Media.Ocr（winsdk 包），本机中文语言包可用：

坑：WinRT 的 IAsyncOperation 不能自己造 event loop 去 await， 要用事件驱动的方式同步等待，否则卡死。

另一个坑：Pillow 装不上（网络/编译问题），索性用标准库 zlib + struct 手写 PNG 编码，零依赖。

硬边界：企微一旦"看不见"，画面就冻结

这是最要命的发现，用内容指纹（对 OCR 行做 md5）做的受控实验：

企微窗口状态 现象 结论
正常显示在屏幕 指纹随新消息变化 ✅ 可用
最小化到任务栏 用户发消息后 70 秒，指纹纹丝不动 ❌ 冻结
移到屏幕外（未最小化） 2.5 分钟无变化；移回屏幕内立刻变化 ❌ 冻结
切到「工作台/文档」页 没有会话列表可识别 ❌ 无内容
被其它窗口完全盖住 仍可读（PrintWindow 强制重渲染） ✅ 可用
在另一个虚拟桌面 仍可读 ✅ 可用

结论：企微必须"真的显示在屏幕上"，且停在「消息」页。 被别的窗口盖住没关系（这是好消息——可以把它藏在后面）。

所以"企微最小化也能实时读到"这个最初的判断是错的，后来被推翻。
